### 2. 第一主线：P-1 技能效果的消费证据（预计可持续多小时）

这是最有价值、也最容易被“看起来绿”误导的缺口。`upgrades-purchased` 证明技能被购买；`skill-combat-effects` 证明战士多重攻击和游侠跳弹链等少数效果；**不能据此声称每种技能在战斗中生效**。先读 `src/engine/modules/content/skills/*.js`、`characters/stats.js`、`characters/character.js`、`combat/skill-effects.js`、`combat/actions.js`、`simulation/characters.js` 与现有变异器/场景。

交付一张可回源的 `statType → 技能定义/职业/升级入口 → 被修改的字段 → 运行时消费点 → 可观测结果 → 当前证据等级` 映射。对每条消费者区分“只出现在注释/序列化/显示/死分支中”与“真实战斗决策读到了它”；静态 `rg` 命中不等于执行证据。若做脚本审计，须对动态属性访问和原型后挂载的漏报显式标记，不允许用“至少一个读点”自动判定全部 PASS。

按技能族而非按文件名切片：优先选一个尚无直接效果断言、能在固定 RNG 下稳定触发的主动族，再选一类被动属性族。使用真实购买/升级路径或与原版同构的输入变异器，使**原版与重构版各自**购买并消费技能；对直接效果、统计变化、浮动文字、伤害/治疗、状态或行为事件作有因果关系的观察，最后比较完整存档。若仅靠 DTO 终态无法区分“技能生效”与“技能被记入存档”，给 harness 加只读观察器，不修改 RNG 消费或原版源码。为新增断言做反向破坏：临时切断重构版消费点，应当变红；恢复后单跑和完整矩阵都绿。避免写几十个重复场景；可复用表驱动的场景定义，但输入和期望不能只从同一实现抄出来。

每个已处理技能族写清“覆盖定义数/总定义数、动态消费点数、没有触发的分支、原版对应证据”。**只有逐项缺口真正闭合，才把 P-1 从 PARTIAL 改 PASS**；否则保持 PARTIAL 并精确缩小缺口。这条主线即使到 8 小时仍未全部完结，也应交付映射表、已验证族和下一族最小入口。不要牺牲完整回归去追求表格的 100%。
