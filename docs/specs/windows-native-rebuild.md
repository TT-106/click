# Clickpocalypse II：原生 Windows 引擎、素材管线与首版交付规格

状态：本地规格，尚未发布到项目问题追踪器。

## Problem Statement

玩家希望在 Windows 上离线双击运行一款保有 Clickpocalypse II 原版挂机玩法、数值、像素美术和辨识度的桌面游戏。现有恢复工程虽然已脱离归档原脚本运行，但仍是浏览器产品，规则、绘图、素材和存档的边界不够清楚，无法作为用户要求的全新原生引擎交付。当前素材依赖图集坐标表、动画定义及散落于界面的路径和裁切值，后续新增地图、职业或技能容易漏图、错帧或意外影响原版规则。玩家也希望未来能加入搜打撤、基地、主线与角色获取，但首版必须先完整保住原挂机体验。

## Solution

交付包含全部正式素材、离线可双击运行的 Windows 桌面包。使用 Godot 4 .NET/C# 实现窗口、像素世界、特效和桌面界面，另建不依赖 Godot 的纯 C# 规则核心。新引擎重新设计状态与模块接口，不导入旧 JavaScript 引擎；归档原版只用于行为对照，经单独验证的纯算法可以用新接口重写或复用。

本体默认运行原版规则。玩家可按新格式存档选择项目内版本化内容包；选择先成为待启用内容包，等队伍回到世界地图且当前战斗、掉落和行动结算完毕，先备份再启用。正式新增内容仅影响以后生成和以后选择的对象。首版建立地牢主题、可玩职业、自动施放技能的扩展机制，用不进入正式游戏的样例证明全链路。素材通过版本化清单统一登记、校验、预览和打包。第二阶段再用可玩的搜打撤竖向样例验证新循环，随后设计基地、主线和角色获取。

## User Stories

1. 作为 Windows 玩家，我希望解压桌面包后双击游戏即可离线启动，以便不用安装网页运行环境。
2. 作为玩家，我希望游戏包自带正式玩法所需的全部像素素材，以便断网时地图、人物、物品和特效仍完整显示。
3. 作为玩家，我希望调整窗口大小并切换全屏，以便按自己的桌面安排游戏。
4. 作为玩家，我希望在 1280×720 和 1920×1080 窗口下看清地图、战斗、文字与面板，以便长时间挂机时能迅速理解当前状态。
5. 作为玩家，我希望原 740×450 世界视野按整数倍清晰显示，以便保留像素画风和原版逻辑可见范围。
6. 作为玩家，我希望窗口增加的空间用于更清楚的信息与操作面板，以便查看角色、装备和进度。
7. 作为玩家，我希望缩放、切全屏和打开面板不改变游戏回合或随机结果，以便界面操作不影响挂机进度。
8. 作为玩家，我希望保留原版组队、职业选择及角色成长，以便继续熟悉的挂机开局。
9. 作为玩家，我希望队伍自动探索世界、地牢与城堡，以便保留原版持续多日的游玩节奏。
10. 作为玩家，我希望移动、寻路、遇敌和战斗遵循原版规则，以便同样的开局产生可对照的进程。
11. 作为玩家，我希望角色按原版 AI 选择目标、攻击、施法和使用物品，以便无需手动逐次指挥战斗。
12. 作为玩家，我希望装备、物品、掉落、背包和商店保留原版数值与获取流程，以便原有养成路线仍有效。
13. 作为玩家，我希望点数、升级、成就、统计、农场与城堡进度都可用，以便原版系统没有因换引擎而丢失。
14. 作为玩家，我希望胜利、续战和重置依照原版语义工作，以便长期进度有熟悉的结果。
15. 作为玩家，我希望所有原版可见的游戏操作和快捷键在桌面程序中可用，以便不依赖浏览器脚本操作游戏。
16. 作为玩家，我希望战斗中的像素特效、伤害反馈和面板状态同步且清楚，以便在未暂停的实战中看懂发生了什么。
17. 作为玩家，我希望游戏运行流畅且点击、按键后的可见反馈及时，以便桌面版优于旧浏览器体验。
18. 作为玩家，我希望每五分钟自动保存并在正常关闭时完成保存，以便进度不会因退出而丢失。
19. 作为玩家，我希望拥有多个独立存档槽，以便尝试不同队伍或内容包组合。
20. 作为玩家，我希望默认把存档放在 Windows 用户数据目录，以便移动或更新程序包时保留进度。
21. 作为玩家，我希望通过显式便携标记切换到程序目录存档，并看到当前存档位置，以便自行决定如何携带游戏。
22. 作为玩家，我希望通过导入、导出和备份管理新格式存档，以便转移进度和恢复误操作。
23. 作为玩家，我希望切换存档位置时由自己复制或导入进度，以便不同位置的存档不会被悄悄合并。
24. 作为玩家，我希望损坏或不兼容的存档保留原件并显示可理解的原因，以便有机会恢复。
25. 作为玩家，我希望游戏最小化时可按原回合节拍继续模拟且停止绘图，以便挂机不浪费绘制资源。
26. 作为玩家，我希望关闭后台进度后，在窗口恢复时一次大时间间隙最多触发一次原规则正常模拟调用，并有说明文字，以便明白该选项的实际效果。
27. 作为玩家，我希望离线进度遵循原开关、两分钟起算门槛和时长上限，以便重开后的收益符合原版预期。
28. 作为玩家，我希望重开时可跳过离线结算，以便自行决定是否追赶停机时间。
29. 作为玩家，我希望手动暂停只在本次会话有效，以便重启后不会无意长期停滞。
30. 作为玩家，我希望能为一个新格式存档明确选择内容包及其版本，以便决定该存档以后会出现哪些新增内容。
31. 作为玩家，我希望待启用内容包在安全激活点先备份再生效，以便当前地牢或城堡和已有随机结果不被中途改写。
32. 作为玩家，我希望新增地牢主题只用于以后生成的地牢，以便已经生成的世界与当前实例保持完整。
33. 作为玩家，我希望新职业在既有组队或职业选择入口出现、新技能在学习后自动施放，以便内容符合挂机玩法。
34. 作为玩家，我希望缺少已启用内容包或版本不兼容时暂停载入并显示具体包和版本，以便补齐或迁移后继续，而不是丢失角色或物品。
35. 作为玩家，我希望仅待启用的包缺失时仍可继续本体进度，并看到该包暂不能激活的提示，以便现有存档不被无关缺图锁住。
36. 作为玩家，我希望未启用任何新增包时，玩法和随机轨迹仍保持本体规则，以便默认存档不受扩展机制干扰。
37. 作为内容作者，我希望把新图片放入所属的项目内内容包并登记稳定视觉 ID，以便统一引用地图、角色、物品和技能画面。
38. 作为内容作者，我希望单图可默认整图导入，图集和动画可显式声明裁切、帧与方向，以便原像素素材和新增素材都能准确呈现。
39. 作为内容作者，我希望导入器在构建前检查缺图、重复 ID、哈希、越界裁切、无效帧和规则引用，以便错误不会进入正式 Windows 包。
40. 作为内容作者，我希望看到导入后的预览并追踪素材与内容包版本，以便确认原图集转换和以后新素材的结果。
41. 作为内容作者，我希望新增同类型素材无需修改世界绘制或面板逻辑，以便后续扩展地图、职业和技能更容易维护。
42. 作为开发者，我希望规则核心、会话编排、存储与素材适配、Godot 展示分别有清楚的依赖方向，以便重构后不再形成全局游戏对象和大循环依赖。
43. 作为开发者，我希望规则核心可独立编译、运行和测试，以便在没有 Godot 窗口时验证数值、时间与随机行为。
44. 作为开发者，我希望第二阶段能连接长期进度与新的搜打撤玩法会话，以便未来增加物资、基地、主线和角色获取而不改写本体规则。
45. 作为验收者，我希望通过同种子空白开局、实战画面、存档故障和本机性能证据判断是否可以切换产品入口，以便不把旧浏览器测试的历史通过状态误当成原生版完成证明。

## Implementation Decisions

- **原生边界**：Windows 首版采用 Godot 4 .NET/C# 展示层、独立纯 C# 规则核心。最终发行包不包含 WebView、旧 JavaScript 引擎或浏览器入口；归档原版仅为行为参照。
- **依赖方向**：展示层将输入转成命令；应用会话层负责命令排序、时间策略、存档及内容包事务；规则核心独占权威状态、内容规则版本与显式随机流；外围适配器提供文件、系统时钟和素材加载。核心不得依赖 Godot、文件路径、墙上时钟或纹理对象，项目依赖图必须无环。
- **规则接口**：一次模拟推进接收已排序的命令、明确时间量与已校验的不可变规则目录，产生语义事件和只读投影。展示频率、窗口状态和面板操作不得推进回合或消耗随机数。领域对象和接口使用表达玩法含义的现代命名。
- **原版对照**：本体复现原版数值、随机算法及消费顺序、250 毫秒回合节拍和各功能链。只允许在单独验证后复用纯算法；新引擎不导入旧模块。新格式存档不读取旧版存档。
- **时间策略**：正常前台、最小化、窗口恢复、休眠、离线及暂停均经应用会话层进入同一模拟入口。后台进度开启时继续原节拍模拟但停止绘图；关闭后一次大间隙最多触发一次原规则正常模拟调用。自动保存间隔为五分钟；正常关闭原子保存；离线按原开关、两分钟门槛和原时长上限结算，允许跳过。暂停不跨重启保存。
- **桌面画面**：保留 740×450 逻辑世界视野，最近邻整数倍显示；桌面面板使用额外窗口空间。展示层分开世界绘制、特效、面板、输入映射和主题布局，场景脚本不承载战斗、掉落或进度规则。
- **存档**：新格式有版本和独立槽位，记录内容包启用与待启用清单、随机流与规则版本。默认使用 Windows 用户数据目录；显式便携标记让下次启动改用程序目录。切换位置不自动合并，提供路径显示、导入、导出和备份。
- **内容包激活**：正式新包按存档显式选择。队伍离开当前地牢或城堡、回到世界地图且战斗、掉落、行动全部结算后，完整校验、先备份、再激活并原子保存。失败时保持完整旧态或完整新态。已生成世界和当前实例不追溯改写；新地牢主题只用于后续生成，新职业和技能从既有选择或学习入口进入。
- **缺包策略**：已启用包缺失或版本不兼容时保护原档、暂停载入并显示所需包及版本，恢复包或经验证迁移后继续。仅待启用包缺失时保留选择、暂停该包激活，本体进度可继续。
- **素材管线**：原始像素素材保持可追溯；旧坐标与动画定义仅供一次性转换。运行来源为按包版本管理的中性素材清单，使用命名空间稳定视觉 ID，声明源文件、哈希、裁切或帧、方向、用途及规则引用。导入器在构建前统一验证并生成预览，Godot 统一解析；不得在正式构建里静默替图。首版由开发者在构建前导入并随包发布，不提供玩家运行时任意图片导入。
- **扩展范围**：首版仅以不进入正式游戏的地牢主题、可玩职业和自动施放技能样例验证包注册、加载、显示、存档和规则隔离。本体为默认规则。第二阶段只预留长期进度与独立玩法会话边界；不提前设计万能玩法插件。
- **切换方式**：平行完成新引擎和原生包，在行为、结构、画面、性能、存档与资源门槛全部通过后整体替换产品入口。

## Testing Decisions

- **主要测试接缝**：以应用会话边界作为唯一新增的可编程验收入口。从空白开局提供种子、可控时钟、已校验内容目录和有序玩家命令，按指定时间推进；读取语义状态投影、事件轨迹、随机流消费位置与新格式存档结果。此入口贯穿规则核心、时间策略、内容包激活和存储适配，优先检查玩家可观察的结果，而不测试私有方法或场景节点布局。
- **原版参照**：现有浏览器差分与场景测试展示了相同种子、回合和行为对照的先例，但它们依赖旧存档和浏览器环境。新验收必须用从未载入旧档的双方空白开局脚本；旧档只可辅助原版端研究长尾行为。先以功能清单为起点查漏，再对地图生成、组队与 AI、战斗和技能、掉落装备、各类升级、成就、农场、城堡、离线、胜利与重开逐条留下可复跑证据。
- **确定性**：相同种子、时钟、命令与推进量应得到一致的语义状态、事件和随机消费位置。改动绘图频率、窗口大小、全屏或打开面板后，以上结果仍一致。样例包关闭时应与本体轨迹一致；启用包后只允许由该包版本引起未来行为变化，已有实例版本不变。
- **存档与内容**：从应用会话边界验证自动保存、正常关闭、导出导入、双存档位置、多槽位、损坏档、缺少已启用包、仅待启用包缺失、迁移及重启。分别在备份、激活、原子保存注入失败，重启只能得到完整旧态或完整新态。
- **素材**：构建期用缺文件、重复 ID、哈希不符、越界矩形、无效动画方向、缺规则引用与错误包版本作为反例；对原图集转换做像素对照和预览审查。检查最终包中的实际资源，而不只检查源清单。
- **桌面黑盒验收**：在本机 Windows 双击离线包启动，检查可调整窗口、全屏、键鼠操作、路径显示、保存恢复和异常日志。在 1280×720、1920×1080 和当前显示器全屏下，截取未暂停的世界地图、地牢、战斗、自动施放特效及主要面板并人工审看清晰度、裁切和反馈；暂停截图不能代替实战截图。
- **性能**：记录本机显卡与测试场景，在 1920×1080 未暂停实战连续 10 分钟，目标 60 FPS、95% 帧耗时不超过 16.7 毫秒、95% 输入到可见反馈不超过 100 毫秒；保留帧时间分布和输入记录。长时间模拟另检查内存、进度与稳定性，不把无界面高速模拟当成真实画面性能。
- **结构与发布**：独立编译和测试规则核心，检查项目依赖无环与现代命名；扫描正式包无旧 JavaScript 引擎或 WebView，并确认所有正式素材在断网环境可加载。只有新引擎逐项通过后才切换产品入口；历史浏览器测试通过状态不能直接继承。

## Out of Scope

- 旧版浏览器存档导入，以及让新格式存档被旧客户端读取。
- 第三方浏览器用户脚本、DOM 选择器兼容、网页发行包及 WebView 桌面封装。
- 玩家在运行时导入任意个人图片、公开第三方模组接口或热加载。
- 首版正式发布新地牢主题、新职业或新技能；样例只用于验证扩展机制。
- 首版实现搜打撤、物资撤离、基地升级、二次元主线和角色获取；这些属于第二阶段产品工作。
- 首版支持 Windows 以外平台或承诺未测试机器上的性能。

## Further Notes

- 当前约定尚待用户整体确认；本规格整理已讨论决策，不表示新引擎或 Windows 包已经完成。
- 本地仓库未配置项目问题追踪器或远端，暂无法发布并设置 `ready-for-agent` 标签。发布位置须由项目设置提供。
- “素材导入”依此前项目内内容包决定解释为开发期流程；若用户另行指定玩家运行时导入，应修订内容包边界和本规格。
