# 游戏产品方向与待办清单

当前实现统一见 [WORKSTATE](WORKSTATE.md)。已确认方向是低压力自动远征与桌面观赏；采集/个人背包/返程/仓库及Electron窗口基础已经落地，制作/基地、永久角色身份、原野战斗、原创角色/技能和约一周远征尚未完成。经济V1是设计输入，商业路线采用先免费测试、原创发行；各阶段实施并未完成。

本文件维护产品目标和差距；历史批次日志见history，工程优先项见REMAINING-WORK。

## 用户已明确的产品方向

以观赏为主的自动探索、收集与养成游戏。玩家想看时随时打开，能挂在桌面上，看队伍在随机生成的地图中生活和冒险。自动化承担日常操作，玩家可以参与准备、查看和调整，长期不查看也不应产生追赶进度的压力。

一次探险的目标跨度约一周，可以更长或更短。这里的一周是待验证的体验目标；自然日、有效模拟时长、在线观看时长和离线推进的关系尚未定案。远征需要有阶段变化和中途收获，不能只靠提高素材需求、重复采集或等待计时来延长。

基本循环候选：基地准备 → 自动出发 → 探索/采集/战斗 → 营地休整 → 撤离返程 → 整理收获/制作/成长 → 下一次远征。随机世界的生成与一次远征的开始、结束应分别设计；连续世界不必因为远征结束而被清空。

## 建议补充：尚待后续验证和取舍

- [ ] **自动返程与安全策略**：低血量、补给不足、背包满或风险过高时，队伍会休整或返程。玩家离开时不能因等待确认而停在危险中。失败可以损失部分本次收益；永久角色、基地和长期收藏的保护范围须先定案。
- [ ] **离线推进与时间规则**：区分窗口可见、最小化、关闭、断网和电脑休眠。先明确哪些时间继续模拟，再实现有界离线结算；关闭后的进展不能依赖后台画面始终运行。暂停是否阻止离线推进也必须明确。当前网页原野隐藏/关闭不推进；桌面程序运行时隐藏仍探索，关闭/休眠不补收益。离线结算是未来能力。
- [ ] **自动整理与可选管理**：自动装备、分类、存放、制作和重复物品处理应有可解释的默认策略；珍贵物品、收藏和玩家锁定装备不被静默出售。背包不应变成频繁清理负担。
- [ ] **远征回顾**：事件日志、拾取来源、遭遇精英、救援、返程原因和收获对比；玩家晚点打开时也能理解发生了什么。可增加关键事件镜头/截图，回顾不是默认逐帧存整周视频。
- [ ] **观赏节奏**：探索、交战、休息、营地、采集和返程有可见变化；天气、昼夜、队员互动和环境细节分阶段加入，避免长期只看重复走路或静止等待。
- [ ] **长周期的阶段目标**：先验证 30–60 分钟内能看见一次完整的小循环，再验证多小时与约一周的远征；这些是测试切片，不强制把最终远征改短。每个阶段需要不同体验，而不只是更大的掉落数字。
- [ ] **存档、备份与升级兼容**：动态区块状态、背包/仓库、基地、远征事件和生成器版本一起持久化；提供备份、导出/导入和恢复；测试中途崩溃及旧版本记录。长途世界不继续靠无限增大 localStorage JSON。
- [ ] **低功耗与自动恢复**：显示帧率与模拟速度分离，隐藏时停止绘制，低频推进/按时间结算；对寻路卡住、孤岛、不可达资源和异常事件提供合理恢复方式，不能以穿墙/瞬移到未知地点掩盖故障。
- [ ] **无追赶压力**：建议不设强制日常、过期材料、错过就失去的奖励或强制竞争排行；默认低打扰通知。挑战主要考验长期准备、队伍组合和策略，不惩罚没及时打开窗口。
- [ ] **主线与日常探索并行**：主线准备和挑战可更难，普通远征仍可持续；稀有材料应有可理解的来源与保底/替代路径，避免一个关键材料随机几周都不出现。具体规则后续再设计。

## 建议实施顺序

1. **短循环与可靠记录**：可保存的资源/交互、每人背包、基本遭遇、自动返程及收获结算。先证明观看价值与安心自动化，再扩长远征。
2. **角色与养成样板**：一个二次元角色完成多方向行走和一套连贯技能动作，配合一组材料/工具/装备及少量基地设施；建立复用的内容导入方式后再扩到多角色、多技能。
3. **长周期与桌面体验**：离线时间规则、长途动态世界保存、回顾、低功耗、小窗/置顶、专属 UI；用真实长周期测试检验一周目标。
4. **内容与剧情**：更多生境、资源、建筑、怪物和精英；最后启动世界观/大纲与主线章节，沿用已经验证的探索和成长循环。

上述排序是建议，不构成本轮开始实现全部系统的授权。原创角色、技能、怪物和剧情仍未设计；材料/生产已有ECONOMY-BASE-DESIGN-V1草案且未接线；没有固定排期、定价或销售承诺。

## 发行与收费建议

建议以 **Windows 桌面应用作为正式产品，网页作为试玩和开发验证入口**。这是基于“长期放在桌面、随时观赏、低打扰、本地长期记录”的产品判断，市场验证尚未完成；技术上已有Electron试用，正式发行取舍见商业规划。

| 方面 | 网页形态 | 桌面形态 |
|---|---|---|
| 开始体验 | 链接即可试玩，适合展示和传播 | 需要下载/安装，适合长期使用 |
| 桌面观赏 | 独立浏览器窗口可用；置顶、托盘等能力不属于普通网页的标准体验 | 可以提供独立小窗、置顶和托盘等桌面行为 |
| 后台与关闭 | 浏览器存在后台限频；关闭后需离线结算或服务端推进 | 可以控制后台策略，但关闭/休眠同样需离线结算；不应靠持续高帧率解决 |
| 长期记录 | 浏览器存储、备份与换设备需要产品设计 | 本地存档/自动备份更容易成为明确的文件工作流；云同步仍需另做 |
| 收费路线 | 自建付费访问需要支付、账户与访问权限；平台内网页支付能力要按渠道核实 | 可考虑下载版买断，以及后续内容扩展；平台与定价待测试 |

建议先验证买断路线；内容扩展和外观可以后续评估。依赖体力、失败复活收费、加速材料或定时付费窗口，会削弱用户提出的安心观赏目标。付费提供完整体验与持续内容的价值，具体价格等可玩样板和目标用户反馈出现后再确定。

技术上已用Electron复用JS/Canvas验证基础窗口和磁盘存档；长期功耗/稳定性仍待验证。桌面应用并不要求马上重写游戏。已有 Godot 分支仍按 [分支约定](BRANCH-WORKFLOW.md) 保留，本轮不改变其目标、不合并 worktree、不启动原生重写。

## 开发前仍需确认的少量规则

1. “约一周”指自然日还是累积模拟时长；是否默认离线推进，以及暂停/休眠的行为。
2. 撤离失败最多损失什么，永久成长和本次携带战利品分别如何保护。
3. 当前已采用个人袋+营地仓库；永久角色身份、未来装备/锁定物归属、基地整理和升级自动化的默认程度仍待确定。
4. 默认四方向是否满足正式美术；八方向、装备外观和更多动作的投入放在哪个阶段。
5. 保留恢复版作为参照/兼容模式与制作原创商业作品之间的边界，以及授权情况。

这些问题目前记录为待办，等对应阶段开始时再细化，不要求用户现在逐项回答。
