# 性能复测（真实浏览器帧时间）— performance-after

> 复现：`npm run dev` 后 `npm run perf:frames`（原始脚本 `scripts/measure-frames.mjs`，采样数由 `FRAME_SAMPLES` 控制）。
> 与 `docs/performance-baseline.md`（harness CPU 口径）互补：那份说明"模拟本身多快"，这份说明"真实页面每帧花多少"。

## 1. 实测（2026-09-26，Chrome headless，1440×1000，同一台机器）

| 状态 | 帧数 | 平均 | P50 | P95 | P99 | 最差 | >50ms 掉帧 |
|---|---|---|---|---|---|---|---|
| 远征视图（地牢渲染 + DOM 面板） | 599 | 4.17 ms | 4.20 | 4.60 | 5.20 | 7.70 | 0 |
| 冒险点面板（数百行 DOM 刷新） | 599 | 4.17 ms | 4.20 | 4.50 | 5.00 | 8.30 | 0 |

同一次运行内被 `simulation/loop.js:76` 的 try/catch 吞掉的渲染异常（`console.log("Caught error. …")`）：**0 条**。

## 2. 结论与口径边界

- 每帧工作量 ~4ms，最差 8.3ms，**没有一帧超过 50ms**（用户可感知的卡顿阈值附近）；60Hz 预算 16.7ms 有约 3 倍余量。
- 关键口径：**headless Chrome 不受 vsync 约束**，rAF 间隔反映的是"本页每帧做多少事"，不是"显示器刷新节奏"。因此这些数字可以用来比较工作量、判断余量，**不能**当作真机 60/120Hz 下的掉帧率。
- 面板切换前后（远征视图 vs 冒险点面板）平均帧时间没有差别（4.17 vs 4.17ms），说明当前规模下 DOM 刷新不是热点；这与 harness 口径的结论一致：模拟只占回合预算的 0.03%，渲染与 DOM 才是帧时间主体，而两者都还有余量。

## 3. 未测与不宣称

1. **没有原版页面的同口径基线**：`archive/original/index.html` 的开局流程未被测试自动化（原版没有新 UI 壳的建队按钮路径），因此本报告**不宣称**"重构版帧时间与原版持平"，只宣称绝对工作量。CPU 口径的原版对比在 `docs/performance-baseline.md`。
2. 未测：真机（有 vsync）、法术特效密集期、几百件背包、地牢切换瞬间、低端设备。
3. 本阶段**没有任何优化提交**：按规范 §29 的纪律，没有热点证据就不动手；上面两组数据说明当前不需要动。若将来出现 >50ms 帧，验收门槛是"假设 + 基线 + 改动 + 新测量 + parity/34 场景全绿"（规范 §84）。
