# 下一阶段执行提示词：Clickpocalypse II 架构现代化

> 适用仓库：`D:\下载\clickpocalypse2-main`。本提示词依据 2026-09-27 的代码和文档编写；开工时必须重新取证。可将下方“交给开发代理的提示词”整体复制到下一次任务中。

## 交给开发代理的提示词

你是负责继续重构 Clickpocalypse II 的开发代理。请全程用中文交流，在 Windows 工作区 `D:\下载\clickpocalypse2-main` 操作。目标是让后续功能开发和维护更容易：缩小调用者需要理解的接口、减少领域逻辑对全局可变状态的依赖，并保留原版游戏的可观测行为。请从第一性原理判断每个改动是否真正减少维护成本，并主动寻找会推翻你方案的反例。

### 1. 先确认当前状态，不得沿用过期结论

按顺序阅读：`docs/WORKSTATE.md`、`docs/REMAINING-WORK.md`、`docs/architecture.md`、`docs/m10-type-debt.md`、`REFACTOR_REPORT.md` 附录 A、`docs/reverse-engineering/facts.md` 与 `unresolved.md`、`MIGRATION_MAP.md`。再检查 `git status --short --untracked-files=all`、`git log -6 --oneline`、`package.json`、`tsconfig.json` 以及实际源码。`docs/HANDOFF-PROMPT.md` 记录的是 U112 时的旧状态，其“继续 M12”“51 行全 PASS”等内容已经过期；遇到冲突，以当前代码、可复跑测试和最新证据为准，并修正文档。

本提示词编写时，历史扫描曾报告 10 项门禁通过、60 个差分场景、验收矩阵 44 PASS / 7 PARTIAL、混淆属性名 0。**这些是历史结果，不是当前全绿保证。**当前实测 `npm run typecheck` 退出码 0；`npm run lint` 退出码 1，因为根目录出现一个未跟踪、0 字节、文件名含不可见字符的文件。另有数个未跟踪的 0 字节文件。先用 `node scripts/find-invisible-name-files.mjs` 和文件元数据查清来源，记录原状；确认是可丢弃的误生成文件后再安全清理，不能把任何未跟踪文件默认当作垃圾，也不能修改或丢弃用户正在进行的工作。随后逐项建立新的门禁基线，记录命令、退出码与日志路径。

### 2. 架构判断依据与不可破坏的契约

现有系统并非待从零开始的单体：原版冻结在 `archive/original/`，产品 UI 经 `src/engine/adapter.js` 访问引擎，77 个引擎模块按领域放在 `src/engine/modules/`，有差分、浏览器、存档和性能检查。已经完成的 M12 字段改名不是下一阶段主线。真正的维护瓶颈是：

- `runtime/index.js` 调用大量 `initialize*()`，顺序本身属于运行契约；
- `runtime/game.js` 组合并持有全局单例，同时反向导入各领域模块；当前扫描有约 48 个模块直接导入 `game`，循环依赖由初始化顺序维持；
- 领域逻辑、DOM 视图、渲染和持久化仍有交叉；目录拆分本身不能证明依赖方向单一；
- `tsconfig.json` 使用 `checkJs`，但 `strict` 为 `false`，`save-dto.js` 的 `SaveData` 类型尚未接入序列化/恢复，`@type {any}` 当前为 42 处；“tsc 无错误”不能写成“类型完备”；
- 既有差分主要比较存档状态；运行时未序列化的状态、UI 路径和真机体验需要各自的观察证据。

不得改变游戏数值、概率、RNG 算法或随机调用顺序、回合和离线节奏、原版像素素材及内容、存档 JSON 键或编码格式、`C2_V1_001` 键、已有 DOM/userscript 契约。保持 `archive/original/**`、原版 fixture 与 vendor 文件原样；原版缺陷应记录而非顺手修复，除非用户另行明确要求玩法修订。不得为了架构图好看而全面重写、引入框架/依赖、机械消除所有循环或添加一层只转发调用的空壳。对外接口应让调用者少知道内部状态、初始化顺序和异常细节；只在确有生产与测试等两个用途时引入新的可替换接口。

### 3. 第一阶段：建立可复核的架构债基线

只读审计以下路径：`src/engine/modules/runtime/{index,game}.js`、`src/engine/{adapter,internal-api}.js`、`src/app.js`、`src/services/saves.js`、`src/engine/modules/{progression,persistence,simulation,views}/`。用脚本或静态分析生成模块依赖清单，至少报告：直接导入 `game` 的文件数及目录分布；强连通分量/循环依赖；初始化顺序的实际依赖；产品 UI 是否绕过 adapter；存档 DTO 在类型检查中的实际使用情况；最常被跨目录读取或改写的状态。把**有证据的事实**和**设计推断**分开写入 `docs/architecture-debt.md`。

选出两个候选切入点，按“给未来功能带来的修改范围缩减、接口简洁度、行为风险、现有测试能否验证”比较。优先考虑成就进度计算，再考虑相邻的冒险点/统计；若代码证据表明另一处更有价值，可以改选，但要写出反例及理由。先写一张简短的迁移卡：当前调用关系、拟定接口、明确的状态所有者、被保留的兼容入口、可观测行为、需要的测试和回退方式。不要只交设计文档；完成后继续实施首个切片。

### 4. 第二阶段：完成一个纵向切片

默认切片是 `src/engine/modules/progression/achievements.js` 的 `getAchievementProgress` 与 `hasVictoryAchievement`：将实际判定逻辑收进以明确数据为输入的模块接口，使其可以不启动 `runtime/index.js` 或借用全局 `game` 就被直接测试；原调用路径保持兼容。切入点和新接口必须由源码证据决定，不要仅因为“纯函数”而额外增加多层包装。注意原版未知 `requirementType` 的返回行为，以及 type 16 的队伍最大等级、type 23–27 的胜利统计，不得把所有 case 简化成同一种字段读取。

按定义表枚举所有真实 `requirementType`，加入表驱动检查，并让至少一条与原版对照的差分场景实际驱动临界值或奖励路径。测试需断言两端各自发生期望变化，再比对完整存档；只比较两端相等不足以证明代码路径被执行。对新断言做一次反向验证：临时制造目标条件失败，确认检查确实报错，再恢复。优先通过新模块接口测试行为，避免测试固化内部实现。

首个切片完成后，报告修改前后的直接单例读取、跨模块知识量和调用者所需接口；用具体调用点说明维护成本如何下降。若减少一处 `game` 导入需要大量转发参数或会扩大接口，停止该方向并记录失败方案。**不要把“模块数增加”当作成果。**

### 5. 第三阶段：依证据扩展，不做一次性大迁移

首切片稳定后按以下顺序评估，每次只做一个可独立回归的切片：

1. **相邻领域依赖**：在 `progression/` 内选择下一条高耦合路径，保持点数、成就、统计与重置语义；让状态读取集中于少数明确位置。用调用点变化与测试难度变化决定是否继续。
2. **存档类型契约**：检查 `persistence/save-dto.js` 的 schema 与真实原版 fixture、空白档、已初始化档的差异；必要时区分这些形态，然后逐函数接入 `game-save.js`。不得通过 `any`、宽泛断言或更改存档键使类型检查变绿。验证导入、导出、损坏档回退、刷新恢复和离线恢复。
3. **产品接口**：检查 `adapter.js` 的快照/命令是否泄漏 DOM 细节、可变对象或内部初始化顺序；只在现有功能切片中收窄接口。`src/app.js` 与 `src/ui/*` 应继续通过 adapter 访问游戏；维护 `c2c.user.js` 依赖的选择器。不要为此单独改版 UI。
4. **证据缺口**：优先补与你修改路径相关的 PARTIAL。完整清单见 `docs/REMAINING-WORK.md`：技能效果、法术 cat=15 的直接观察、远古稀有度、成就条件、多版本真实存档、真机长期运行、更多 Canvas 状态/视口。没有真实历史档或设备时如实保持 PARTIAL，不许用构造数据冒充真实样本。

每个切片均先证明需求和接口，再编码、验证、复核 diff、更新文档。只有结果能降低未来改动的传播范围才继续扩展；否则保留测试与调查结果，回退错误设计。迁移卡与结论写入 `docs/architecture-debt.md`，`docs/architecture.md` 更新实际依赖图，`docs/WORKSTATE.md` 记录最新可复跑状态。不要复制现有报告中过期的场景数、门禁结果或百分比。

### 6. 验证门禁与失败处理

在 PowerShell 中逐项运行并检查 `$LASTEXITCODE`，不要用管道末端的退出码冒充测试成功。开发服务器由 `npm run dev` 提供，浏览器门禁开始前确认 `http://127.0.0.1:4173` 可访问。对涉及引擎、存档、渲染的切片，至少跑 `npm run typecheck`、`npm run check`、`npm run test:parity`、`npm run test:scenarios`、`npm run test:e2e`；收官时再逐项跑 `npm run lint`、`npm run build`、`npm run test:soak`、`npm run perf`、`npm run perf:frames`。`npm run build` 单独执行，避免本机文件操作限制干扰。代码文件变更后先做语法检查；最终执行 `git diff --check`、`git diff --stat`、`git status --short --untracked-files=all`。性能只与同口径基线比较，不把单次波动或 headless 帧间隔写成真机收益。

如门禁失败，先分辨是当前工作区已有问题、测试设施问题，还是新代码引起的分叉；保留失败日志和最小复现。不得调低断言、改变指纹算法、修改原版源码来“修绿”。如果当前未跟踪文件导致 `lint` 失败，要先独立处理并如实记录，不把该失败归咎于后续架构切片。

### 7. 最终交付格式

交付已经落地的代码和文档，而不只是下一份计划。最终报告用中文列出：

1. 已完成的切片及每个接口为何更容易调用、测试和维护；前后依赖数据。
2. 行为与存档兼容的证据：具体测试命令、退出码、场景和日志；每个 PARTIAL 是否真正缩小，不能把 PARTIAL 写成 PASS。
3. 尚存的架构债、被否决的方案及原因、需要用户提供的外部样本或真机条件。
4. 修改文件、未跟踪文件和未提交改动的状态；若提交，每个独立切片一个可回退提交，不夹带无关文件。

常规可逆实现请直接推进。只有需要改变原版玩法、修复原版固有缺陷、另行重设计 UI，或必须使用用户未提供的真实历史存档/设备时，才向用户说明具体决策点。
