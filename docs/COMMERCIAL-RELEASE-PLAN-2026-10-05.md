## 2. 从第一性原理定义“可以收费”

用户花钱获得的价值，是一支有辨识度的队伍在自己的桌面上持续生活、探索和成长；材料带来新能力，观看带来变化，离开也安心，回来能理解发生了什么。

因此至少要同时满足六个条件：

1. **有权提供**：产品中每一类代码、文字、角色、图片、字体、音频、名称与商店材料，来源和分发条件清楚。
2. **有实际乐趣**：玩家能体验完整循环，而不是等待尚未开放的系统。
3. **有可靠记录**：升级、关闭、休眠和异常不随意吞掉长期成长。
4. **能在目标设备运行**：普通用户无需开发环境；后台不影响工作，性能承诺有真机证据。
5. **有清楚的交易**：购买内容、价格、免费测试的边界、更新方式、退款和客服路径明确。
6. **能继续服务**：出现问题有负责人、诊断办法、修复包与对账方式。

对抗性问题：

- 如果删除“正在开发”和“未来会有”，当前体验是否还值得留下？
- 如果玩家一天不看，回来能否理解变化，而非只看到库存数字？
- 如果普通种子连续没有皮革，主干进度能否继续？
- 如果存档升级到一半断电，是否还能恢复到一个完整状态？
- 如果小窗让笔记本风扇持续转，玩家为何要让它陪伴工作？
- 如果将原游戏名字换掉，发行包是否仍启动了原作派生核心？
- 如果下载量很好，但没人持续使用，是否应继续增加内容而非停下来改体验？
- 如果有人付钱后遇到严重故障，谁在什么时候负责回应？

这些问题决定优先级。代码量、配方数量、截图漂亮程度、自动测试通过数都不能单独回答它们。

建议的工程目标需要先在参考机确认后冻结：观赏模式稳定 30 FPS，CPU/内存/耗电不明显影响工作；隐藏时绘制为 0；24h 内存无持续失控增长；活跃 UI 常见操作反馈约 100ms 内；多数保存不明显卡顿。**具体 CPU/内存数值在基线测量后定，不能现在承诺所有机器都达到同一百分比。**

可设参考预算作为讨论起点：普通低端参考机可见时总 CPU 尽量低于 5–8%、隐藏时低于 1–2%，空闲后全部相关进程私有内存尽量控制在约 400MB 内。必须写清 CPU 归一化方式、进程集合、采样时段与硬件；这些是待验证目标而不是当前实测成绩。如 Electron 基础开销无法满足目标，先优化绘制、缓存和调度，再用同一功能样板比较替代宿主，不同时重写所有玩法。

**G5 通过条件**：宣称的时间规则真实生效；跨关闭/休眠/升级仍可恢复；后台和长期资源占用有实际设备数据；自然一周体验至少完成一轮观察。没有做过的系统状态不能出现在宣传承诺里。

### 11.1 三轮测试怎样安排

| 轮次 | 建议人数 | 主要问题 | 参与者任务 | 必须收集 |
|---|---|---|---|---|
| 第一轮 | 5–10 | 别人能否开始、理解、完成闭环 | 不讲解地首次运行；经历一趟；制作/升级；退出重开 | 每一步障碍、帮助次数、错误、是否想继续与原因 |
| 第二轮 | 15–30 | 是否愿意陪伴使用、成长是否有意义 | 按平常生活使用 7 天，不强制每日登录 | 自发回访、状态切换、关机/休眠、最喜欢/最无聊、资源影响 |
| 第三轮 | 30–100 | 内容定位、付费价值、跨机可靠性 | 使用公开版；可自愿体验不同队伍/策略 | 安装成功、版本迁移、关键缺陷、真实推荐、愿付价与拒绝理由 |

招募不是公开越多越好。先修可启动/可理解/不丢档，再扩人数；不同操作系统用户不计入 Windows 首发质量分母后假装通过。

### 11.2 指标定义与建议判断线

以下是内部决策建议，不是行业平均或保证值。每个指标写明分母、样本、版本、时间与未回收比例；小样本用“几人/几人”，不把百分比包装成精确预测。

| 指标 | 怎样计算 | 建议判断线/用途 |
|---|---|---|
| 安装并首次进入 | 成功创建队伍并进入画面的人 / 实际尝试安装的人 | 小规模测试不能反复依赖你远程操作；公开轮目标约 95% 以上，且所有失败能解释/修复 |
| 独立完成小循环 | 无开发者实时帮助完成归仓和一项升级的人 / 有效首测者 | 建议至少 8/10；不足先改引导和界面 |
| 感知成长 | 能解释“这次升级改变了什么”的人 / 完成循环的人 | 不靠背诵教程；把不理解的原话写入任务 |
| 7 天自然回访 | 指定 cohort 中，在定义时段自发再次使用的人 / 首次成功者 | 按加入日计算 D1/D7；关闭离线收益不算主动回访；目标先参考 D7 约 30% 再结合实际使用情境判断 |
| 实际陪伴价值 | 受访者说出具体使用场景并愿继续保留 | 建议至少一半有效受访者有具体价值；朋友迁就和“喜欢作者”单独标记 |
| 技术阻断 | 丢档、不可启动、重复收益、不可恢复卡死数量 | 所有已知阻断问题必须关闭；测试中未出现不等于未来零风险 |
| 功耗打扰 | 因风扇/卡顿/耗电/抢焦点主动停用的反馈 | 每一例都调查设备与状态；不能用更多内容抵消 |
| 愿付价 | 愿买区间与具体原因，及明确不愿买的理由 | 用于选择方案；不乘下载量生成收入承诺 |
| 真实支付证据 | 正式销售后的成交、退款、留用、评价 | 上线后才能验证商业需求；免费测试阶段保持为未知 |

建议访谈问题：

1. 你会在什么时间打开或留着它？最近一次实际这样用是什么时候？
2. 如果明天不能用了，你最会想念哪个具体部分？
3. 哪一刻觉得无聊、困惑或想关闭？有没有真的关掉？
4. 你这几天回来主要看什么？成长对你有什么意义？
5. 小窗、后台、电脑休眠和退出的规则与你预期一致吗？
6. 如果只能改一件事，你选什么？为什么？
7. 若后续成为付费游戏，你会考虑吗？什么范围值得，什么原因会拒绝？
8. 有没有你更愿意使用的替代体验？它好在哪里？

### 12.1 国际平台路线的已核实条件

Steam 要求真实主体、匹配的银行信息、税务问卷和协议，并审核商店/构建。每产品 Steam Direct 费用为 US$100 或等值；这不是项目全部成本。[Steam 入驻](https://partner.steamgames.com/doc/gettingstarted/onboarding)、[Steam Direct 费用](https://partner.steamgames.com/doc/gettingstarted/appfee)

先免费测试可以采用独立测试包、itch.io 免费下载，或满足接入条件后的 Steam Playtest。Playtest 与正式主产品分开处理；具体机制与平台资格按配套研究和后台核实。[Steam Playtest](https://partner.steamgames.com/doc/features/playtest)、[itch.io 创建者文档](https://itch.io/docs/creators/)

### 12.2 中国大陆优先路线

将游戏出版审批、出版/运营合作主体、适用网站或服务的 ICP 条件、内容与未成年人保护、数据与隐私、税务和收款分开核实。是否为单机、本地记录、免费测试、通过境外平台或面向某地区，并不能由我直接推导出所有要求自动豁免。

我准备功能、联网、数据流、销售主体、服务器位置和分发地区的说明；你携此说明与主管机构、专业顾问或适格发行合作方确认具体适用和申请流程。在这条路线里，主体/出版合作/材料/审查可能成为关键路径，不能承诺与国际自发行在同一固定日期收费。官方来源与具体问题清单见配套调研 `research/COMMERCIAL-RELEASE-RESEARCH-2026-10-05.md`。

### 12.3 Windows签名不是“买证书就不会弹提示”

我准备签名流程和干净机器测试；你确认主体、选择服务并支付，保护签名身份与凭据。OV/EV 签名与 SmartScreen 信誉是不同问题，不能保证新包签过名就没有提示，也不能默认大陆个人/公司符合某项云签名服务资格。按 Windows 权责方的当前文档和平台实际结果核实，不为了消除提示盲买昂贵证书。具体资格与官方来源见配套调研。

## 14. 系统级验收矩阵

下面是以后开发批次应覆盖的真实风险。只对有意义的行为和边界写测试，低影响文案/样式用实际检查，不写与实现一模一样的空测试。

| 系统 | 必须验证的正常路径 | 必须攻击的边界/故障 | 通过证据 |
|---|---|---|---|
| 独立启动 | 首次创建队伍→原野→保存→重启 | 没有经典目录、旧图集或原作存档也能启动；包内资源缺失给错误 | 干净产品包 E2E + 来源审计 |
| 角色归属 | 改名/排序/换队不改变物品所有权 | 同名、离队、换世界、迁移到一半失败 | 稳定 ID 断言 + 真实旧试玩档 |
| 世界生成 | 多种子、负坐标、跨区块连续 | 湖泊/孤岛/不可达目标/坐标上界；缓存淘汰重建 | 固定种子与最差案例、路径记录 |
| 资源 | 采集→剩余→耗尽→重载 | 保存恢复重复采、生成规则升级映射错节点 | 节点状态与库存守恒 |
| 负重 | 正常搬运、容量升级、返程 | 超载、速度最低点、队员变动、角色负重质量 | 真实路线与到营地结果 |
| 生产 | 原料→在制→产物 | 双扣燃料、anyOf双扣、重复完成、输出满、原料保护抢料 | 事务测试 + 每个边界保存/重启 |
| 建筑 | 起点→建造→升级→新能力 | 循环解锁、自身预留、未走到前哨就扣货、无外观差异误宣传 | 依赖图 + UI实操 + 收益对照 |
| 装备 | 取得→装备→升级→卸下 | 实例复制、锁定品消失、旧件重复入库 | 唯一实例与质量/数量账 |
| 战斗/技能 | 自动选择→动作→效果→撤退 | 无目标、目标已死亡、路径阻断、掉落结算重放 | 可观察生命/状态/库存变化与录屏 |
| 时间 | 可见/隐藏/暂停/关闭/休眠 | 重复离线结算、负时间、异常大时间、暂停后重启 | 状态矩阵与不重复事务 |
| 保存 | 原子写入→备份→导出→恢复 | 写盘失败、磁盘满、损坏、迁移断电、旧版读新档、路径权限 | 独立测试目录故障注入 + 原档保留 |
| UI | 小窗/管理/背包/基地/技能/回顾 | 125–200%DPI、键盘/减少动画、长文字/高数量、负坐标显示 | 真实 Windows 操作和截图 |
| 桌面宿主 | 置顶、缩放、托盘、暂停、退出 | 双实例、系统关机、渲染崩溃、显示器移除、窗口跑出屏幕 | 普通用户机器/账户实测 |
| 性能 | 30FPS画面、隐藏不画、任务推进 | 大库存/大历史/多区块/几小时缓存增长、唤醒尖峰 | 原始时间序列与分位数，不仅一次截图 |
| 分发 | 下载→解压/安装→运行→升级 | 路径含中文空格、非管理员、无网络、杀软提示、旧包残留 | 实际安装路径 E2E 与签名/包审计 |
| 来源 | 发布允许清单与实际包匹配 | legacy fallback、原作文本/图集、未知字体/音乐、秘密与测试档进包 | 逐项处理台账 + 文件清单核对 |
| 免费转收费 | 版本边界、进度迁移、购买入口 | 原先免费承诺突然收回、买错版本、迁移丢档、试玩假购买 | 页面说明与迁移样本、平台测试路径 |

最低设备矩阵建议：Windows 10/11 是否支持须按发行时仍受支持的 Electron/系统环境确认；至少一台低端或集显参考机、一台常见笔记本、另一台不同 DPI/多显示器机器。不要因开发者机器正常就标所有 Windows 设备支持，不在未验证时宣传 Mac/Linux/Steam Deck。

严重度建议：

- S0：丢档、来源/秘密泄露、重复付费/交易严重故障、无法恢复的长期进度破坏。停止相关发布并优先处理。
- S1：无法启动、核心循环卡死、主要设备持续崩溃、升级无法完成。不得进入付费候选。
- S2：常见操作障碍、明显功耗/显示问题、部分内容不可用。有明确修复或删去承诺后重新验证。
- S3：低影响视觉/文案/少见布局问题。记录并按收益排序处理。

## 15. 具体收费模式如何选择

当前决定是**先测试，收费方式不预定**。建议把三条路线提交给 G6 决策：

| 模式 | 适用信号 | 增加的工作 | 主要风险 |
|---|---|---|---|
| 一次买断 | 玩家愿为完整本地陪伴体验付钱，希望安静使用 | 平台商品与价格、版本权益、售后；未来扩展另评估 | 内容价值不够或更新承诺超过维护能力 |
| 免费核心 + 付费内容 | 免费核心已独立有价值，玩家愿要额外角色/章节/场景 | 内容授权、升级兼容、免费/付费边界、平台 DLC 或权益配置 | 为逼购买人为制造痛点，分割核心体验；维护版本组合变多 |
| 持续免费 | 使用价值成立，但付费证据不足或暂不值得投入商业成本 | 维护范围与预算、明确发展计划；捐赠是否采用另决定 | 把大量下载误当稳定收入，超出自己的维护时间 |

暂不优先订阅、广告和资源加速收费：它们通常需要持续服务/内容供给/支付和权益管理，且可能与低压力桌面陪伴冲突。如果测试给出强理由，再单独立项；不要因为“能接支付”就先实现。

测试时可以讨论若干价格区间，但正式价格应根据完成后的体验、目标用户、渠道地区价与成本模型决定。本计划不先锁定一个价格，也不预测销量。

### 15.1 收入与回本模型

分开统计玩家支付额、平台结算收入、现金成本、你的劳动与机会成本。首次收款也不一定是销售当日到账。

简化模型：

`单份净结算 ≈ 实际平均成交价 × (1 - 退款率) × 综合结算保留系数 - 单份可变成本`

`现金回本份数 = 向上取整(待回收现金支出 / 单份净结算)`

综合结算保留系数需结合实际渠道合同、适用税费与地区销售组合计算，不能把某个平台费率当成全部损耗。现实情况应按销售明细/结算单重算。

**仅用于演算的假设，不是价格建议或收入预测**：平均成交价 38 元，退款率 8%，综合保留系数 0.65，可变成本暂按 0，则每份约 22.72 元；若待回收现金支出 15,000 元，约需 661 份。该算例未计你本人劳动、税务差异及其他未列成本；变量改变须重新计算，不能据此承诺项目赚钱。

预算每周维护一张表：已支付、已承诺未支付、未来必需、可选、由谁支付、取消条件。宣传预算只有在安装成功、内容留用与来源问题处理后再扩大。

## 17. 排期：给出依赖和范围，不给虚假的日期保证

假设：每周持续安排约 4–5 天有效工程推进，批次连续；你每周可给约 3–5 小时集中决策/体验/反馈；有可用第二台设备与测试者；首版范围控制在第3节建议内；必要素材可以复用明确许可来源或合理采购，外包不长时间停滞。

这不是“AI自己全天开发、你完全不用出现”的估算。决策、专业审查、自然时间测试与真实人反馈均可能形成关键路径。

| 相对时间 | 主线交付 | 我在做什么 | 你在做什么 | 停点 |
|---|---|---|---|---|
| 第 0–1 周 | 当前成果保护与产品契约 | 快照、现状、来源初筛、任务板、样板范围 | 市场/主体/预算/核心承诺 | G0 |
| 第 1–5 周 | 独立原创产品核心 | 独立队伍/入口/保存/预览/构建；来源处理 | 名称、疑点处置、审美方向与外部安排 | G1 |
| 第 5–9 周 | 材料→生产→升级小闭环 | 新量纲、普通供给、工坊/炉窑/井、补给/成长与测量 | 体验样板，确认收益和管理压力 | G2 |
| 第 9–12 周 | 小规模免费测试 | 引导/包/反馈工具/修复 | 招募5–10人、亲自连续使用、访谈 | G3 |
| 第 12–20 周 | 原创角色/遭遇/基地 + 长期底座 | 动画/战斗/技能/装备/物流；时间/存储/功耗并行 | 画师或素材合同、每阶段实机验收 | G4/G5 |
| 第 18–24 周 | 公开免费测试 | 公开包、更新、cohort分析、关键修复 | 招募30–100人、渠道/地区确认、收费选择 | G6 |
| 第 24–32 周 | 付费候选与发行准备 | 商店材料、签名分发、渠道构建、迁移与全面验证 | 身份/银行/税/协议、价格、发布批准 | G7 |
| 第 28–36 周窗口 | 正式收费与首月维护 | 发布支持、热修复、对账分析、后续任务 | 发布、客户关系、商业决策 | 30天复盘 |

推荐将**8–12 周内得到第一批有价值的免费测试、18–24 周公开测试、28–36 周进入首版商业发行窗口**作为当前预算估算，G1/G3/G6 分别重估。阶段可并行，因此区间重叠；先完成来源审查或样板较顺利时可以提前，不能提前省略验收。

需要额外增加时间的情况：

- 运行代码来源问题较大：新增约 4–12 周，或重估整个底座。
- 全部角色与环境要求完全委托原创、动作量更大：按外包样板与合同周期另排，不能靠生成单图替代。
- 免费测试显示观看或成长价值不足：每轮增加约 2–4 周产品调整再测。
- 首发加入完整主线、配音、云存档、移动版/多平台：分别立项，不塞入上述范围。
- 中国大陆发行所需主体/出版合作/审批：等待不可由开发速度压缩，另建合规关键路径。
- 只有周末断续推进：按实际有效投入重排，不沿用上述周数。

## 18. 可以并行与不能并行的事

可并行：来源台账与产品规格；独立核心与美术样板；功能开发与测试材料；角色内容与长期保存；公开测试与平台身份材料；平台审核等待与已授权的缺陷修复。

必须顺序：来源不清时不发包；角色规格未定不量产阵容；物品计量/稳定身份未定不做完整装备迁移；生产事务没稳不增加复杂物流；时间规则未定不算离线收益；测试核心价值未成立不大量投广告；付费范围未定不承诺完整游戏价格；最终候选没锁定不批准上线。

主要关键路径：

`来源与独立性 → 新经济事务与成长闭环 → 真实免费反馈 → 正式角色和多日价值 → 保存/功耗/升级可靠性 → 收费选择 → 发行主体与审核 → 最终包 → 首发维护`

任一节点阻塞时，改做独立的下游准备任务，不掩盖阻塞。例如审查等待期间可整理素材规格和测试问题，但不能把未解决的原作依赖包上传给玩家。

| 1 | 当前成果快照、必要基线、代码/内容来源初筛 | 确认首发市场、每周时间与首阶段预算 | 备份/台账/现状表 |

| 3 | 独立角色身份/队伍/保存接口设计 | 查看名称与主题候选 | 可审查的接口与数据例子 |
| 4–5 | 独立最小入口：组队→探索→保存→重开 | 实机体验，指出明显阻碍 | 最小原创产品可运行样板 |
| 6 | 对允许内容构建试验包，审查旧依赖/回退 | 安排第二台Windows机器 | 包清单、来源疑点与运行结果 |
| 7 | 根据审计决定需要重写的基础模块 | 处理必须外部确认的来源问题 | 明确替换表和剩余工作量 |
| 8 | 物品整数计量、稳定实例、旧试玩迁移草案 | 看量纲显示和负重信息 | 数据方案、迁移样本和UI草稿 |
| 9 | 普通材料供给与生产事务小样 | 确认材料有用且管理负担可接受 | 一次真实加工过程与守恒证据 |
| 10 | 汇总G1状态，确定接下来两周闭环切片 | 对小样与预算给决定 | 来源/独立性完成度、下一批范围与证据 |

如果某天前置条件不成立，按问题切换独立任务并记录原因，不写“第10天一定完成G1”。

你现在最先要做的只有三组事：**首发市场与主体；你的时间/现金上限；你希望第一批玩家看见的角色/建筑风格与目标使用场景。** 第一组信息可以先做初步选择，专业确认在对外分发前完成；名称不必在独立核心开工前最终确定。

## 21. 后续每一批怎样交付，避免无限重构

建议每批控制在一个可演示行为，持续约 2–5 个工程日；遇到需要更长的来源/存储/角色批次，先拆最小样板。每周一次约 30–60 分钟产品评审，日常技术选择由我处理，不把每个变量名、目录与像素调整都交给你确认。

每批完成报告必须包含：

1. 本批解决的玩家问题与实际行为变化。
2. 哪些完成、哪些只是草案、哪些有证据缺口。
3. 改动文件范围与保护内容是否保持。
4. 实际检查命令、退出码、日志与截图/录屏/包路径。
5. 当前能运行的版本与SHA256；需要时使用独立测试目录，不操作玩家真实存档。
6. 阻塞问题、我可独立继续做的事、需要你决定的少数事项。
7. 下一批的范围、依赖、预计工作量与通过条件。

执行纪律：

- 开工先核对工作区与现态文档，不以历史任务书当当前事实。
- 不清理、回退或覆盖原有未提交工作；提交只包含当前批确认内容。
- 保留原作恢复线的原版文件、fixture、存档/RNG/节拍保护；原创产品另有规则与测试。
- 来源/保存/库存事务/时间等高风险变动必须做有意义的边界与反向验证。
- 门禁通过后，按本批变化做对应真实网页/Windows包验证；没有新变动或未解决疑点不反复扩大检查。
- 不为“完美架构”阻塞验证；仅处理会影响产品安全、来源独立性和持续开发的结构问题。
- 不凭本计划接触作者、玩家、外包或平台人员；联系与对外发布由你执行或另给明确授权。
- 不自动创建收费商品、注册身份、签协议、付款或发布；先准备可审批的具体材料。
